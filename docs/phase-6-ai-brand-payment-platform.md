# Phase 6: AI-Generated Brand Payment Platform

This plan replaces the current layout-builder-centered demo with a platform
where customers generate their own branded payment interfaces through an AI
generation gateway, while all interfaces integrate with the same internal
payment core through brand-specific API facades.

## Goal

The platform should support three separate concerns:

- a stable internal payment core that owns payment state, history, and
  canonical data;
- a brand runtime layer that exposes unique public contracts per brand and
  maps those contracts back to the payment core;
- an AI generation gateway that asks OpenAI, Gemini, Claude, or another model to
  generate client UI code against only the brand-specific contract, not the
  internal core schema.

The generated interface is the brand. The admin/operator must be able to list
all generated brands, open each brand interface, click through it, and inspect
how it integrates with the payment core.

## Prototype Use Cases

1. Admin creates a brand with unique design, API contracts, status labels, and
   field names. The brand interface is generated by the AI generation layer
   against a configurable system prompt and the public brand contract.
2. End users register or log in inside a specific brand, perform payments, and
   view transaction history. The user-facing contract, labels, and UI language
   should differ enough that users do not see the shared internal platform.
3. The platform behaves like a small Stripe-like payment system: it owns
   registration/login, account payment history, simulated payment execution,
   local scenarios for different payment statuses, and about 10 canonical
   statuses that brand contracts can remap.

## Current Layout Builder Reuse

Reuse these parts:

- `Brand` and `BrandSchema` concepts from `apps/layout-builder`;
- per-brand slug generation and generated field mapping;
- payload structures: `flat`, `nested`, and `key-value-array`;
- palette/logo ingestion for brand identity;
- recent brand listing and admin preview entry points;
- server-side canonical-to-external and external-to-canonical mapping pattern.

Replace or move these parts:

- dashboard/payment data should not live in layout builder request history;
- SVG rendering should become a fallback preview, not the main brand product;
- current `LayoutBuilderDashboardConfig` should be replaced by payment-core DTOs;
- brand app generation should be code/artifact based, not deterministic HTML
  assembled inside `LayoutService`.

## Target Services

### 1. Payment Core

New app: `apps/payment-core`.

Responsibilities:

- create payment intents and payment records;
- transition payments through a controlled state machine;
- store canonical payment history;
- expose stable internal APIs for brand facades;
- emit status-change events for audit and future webhooks.

Initial canonical status set:

```ts
export type PaymentStatus =
  | "created"
  | "requires_payment_method"
  | "requires_confirmation"
  | "processing"
  | "authorized"
  | "captured"
  | "settled"
  | "failed"
  | "canceled"
  | "refunded";
```

The status list is intentionally Stripe-like but simplified. `captured` and
`settled` are separate so a brand UI can distinguish "money captured" from
"money available/settled". `refunded` is terminal for V1; partial refunds and
disputes can be added in V2.

Primary tables:

- `payments`
- `payment_events`
- `payment_methods`
- `payment_customers`
- `payment_intents`
- `balance_transactions`

Canonical payment row for table/history APIs:

```ts
export interface PaymentHistoryRow {
  paymentId: string;
  externalReference: string;
  brandId: string;
  merchantId: string;
  customerId: string | null;
  paymentMethodId: string | null;
  paymentIntentId: string | null;
  status: PaymentStatus;
  amount: number;
  currency: string;
  payerLabel: string;
  destinationLabel: string;
  methodType: "card" | "bank_transfer" | "wallet" | "crypto" | "manual";
  customer: PaymentCoreCustomer | null;
  paymentMethod: PaymentCorePaymentMethod | null;
  paymentIntent: PaymentCorePaymentIntent | null;
  provider: string;
  createdAt: string;
  updatedAt: string;
  authorizedAt: string | null;
  capturedAt: string | null;
  settledAt: string | null;
  refundedAt: string | null;
  failureCode: string | null;
}
```

Internal API:

- `POST /payments`
- `GET /payments/:id`
- `POST /payments/:id/confirm`
- `POST /payments/:id/capture`
- `POST /payments/:id/refund`
- `POST /payments/:id/cancel`
- `GET /payments`
- `GET /payments/history`
- `GET /payments/summary`

MVP gateway-domain progress:

- `payment-core` now stores structured merchant payment data: customers,
  payment methods, payment intents, payments/charges, events, and balance
  transactions;
- `POST /payments` accepts both the old `destinationLabel` shape and the new
  structured `customer` + `paymentMethod` shape;
- `GET /payments/history` returns payments plus structured customers, payment
  methods, and balance transactions for the authenticated merchant account;
- payment rows include nested customer, payment method, and payment intent
  details so brand UIs no longer need to encode card/customer details into one
  display string.

The payment core never exposes per-brand randomized field names. It only speaks
canonical internal DTOs.

### 2. Brand Runtime Facade

New app or evolved layout builder: `apps/brand-runtime`.

Responsibilities:

- own brand records, logos, palettes, deployment metadata, and generated
  contracts;
- generate unique public API routes and field names per brand;
- expose brand-specific read/write APIs;
- validate external brand payloads with Zod;
- map brand payloads to payment-core DTOs;
- store contract versions and request logs;
- serve generated brand artifacts from a controlled runtime.

Public brand API shape:

```text
GET  /b/:brandPublicId/:contractSlug/app
GET  /b/:brandPublicId/:contractSlug/config
GET  /b/:brandPublicId/:contractSlug/payments
POST /b/:brandPublicId/:contractSlug/payments
POST /b/:brandPublicId/:contractSlug/payments/:publicPaymentId/confirm
POST /b/:brandPublicId/:contractSlug/payments/:publicPaymentId/refund
```

Each brand receives:

- unique endpoint slug;
- unique public resource names, for example `orders`, `ledgerItems`,
  `checkouts`, or `paymentCases`;
- unique field names with hashed suffixes;
- one of several payload structures;
- unique status labels mapped to canonical `PaymentStatus`;
- unique table column labels and order;
- unique UI artifact generated by AI.

Important: this layer is an abstraction and isolation boundary, not a real
security guarantee that customers cannot infer a shared backend. Security must
come from authentication, authorization, rate limits, auditing, and strict data
isolation. Contract variation only prevents the internal canonical schema from
being directly exposed.

### 3. AI Generation Gateway

New app: `apps/ai-generation-gateway`.

Responsibilities:

- proxy prompts to configured AI providers;
- keep provider API keys server-side;
- normalize OpenAI/Gemini/Claude responses into one `GeneratedBrandArtifact`;
- require structured output for generated manifests;
- run static validation against allowed frontend capabilities;
- persist generated source/artifacts and model metadata;
- retry or fall back to a local template when generation fails.

Recommended first implementation path:

- use Vercel AI SDK Core for a common TypeScript abstraction across OpenAI,
  Anthropic, and Google providers;
- keep direct provider adapters behind the same interface for cases where a
  model-specific feature is needed;
- use Zod/JSON Schema to force the model to return a manifest instead of
  arbitrary prose.

Provider adapter interface:

```ts
export interface UiGeneratorProvider {
  readonly name: "openai" | "gemini" | "anthropic" | "local";
  generateBrandArtifact(input: GenerateBrandArtifactInput): Promise<GeneratedBrandArtifact>;
}
```

Generated artifact manifest:

```ts
export interface GeneratedBrandArtifact {
  artifactId: string;
  brandId: string;
  provider: string;
  model: string;
  framework: "react-vite";
  entryFile: string;
  files: Array<{
    path: string;
    content: string;
  }>;
  contractVersionId: string;
  capabilities: Array<"read_payments" | "create_payment" | "confirm_payment" | "refund_payment">;
  createdAt: string;
}
```

The prompt must describe only the public brand contract, sample data, allowed
actions, visual brand inputs, and UX constraints. It must not include internal
payment-core DTO names, database schema, service names, or canonical enum names
unless those names are explicitly intended to be public.

Current MVP implementation:

- `apps/layout-builder` exposes `POST /brands/ai`;
- the admin UI sends a brand brief plus an editable system prompt;
- the backend uses `AiBrandGeneratorService` with provider `local` to generate
  a `generationProfile`;
- `generationProfile` is stored in `BrandSchema.fields` metadata next to the
  field mapping and template profile;
- the public preview uses the generated resource alias, action labels, and
  status labels;
- AI-created brands serve a runtime app instead of the old static dashboard
  preview. The runtime app lets a user register/login, create a simulated
  payment, and view brand-scoped payment history;
- brand runtime endpoints proxy to `payment-core` through
  `PAYMENT_CORE_BASE_URL` and map responses back to brand-specific field names
  and status labels;
- OpenAI/Gemini/Claude adapters can replace the local provider behind the same
  service boundary later.

### 4. Admin Console

Evolve `apps/builder-frontend`.

Views:

- brand list with generated artifact status;
- create brand wizard: name, logo, target audience, provider/model, requested
  style, feature toggles;
- generated contract inspector;
- generated app preview in an iframe;
- payment history inspector for that brand;
- request log and mapping debugger;
- regenerate/version rollback controls.

The admin console should be the operator's access point to every brand
interface the customer creates.

## Contract Obfuscation Strategy

For each brand, generate a `ContractVersion`:

- `brandPublicId`: opaque public ID, not the database primary key;
- `contractSlug`: opaque, brand-flavored route slug with entropy;
- `resourceAlias`: randomized domain wording;
- `fieldMap`: canonical field to public field;
- `statusMap`: canonical status to public label/status token;
- `structure`: `flat`, `nested`, `key-value-array`, or V2 custom sections;
- `tableProfile`: column labels, column order, visibility, density;
- `samplePayloads`: generated from real canonical DTOs after mapping;
- `capabilities`: allowed operations for the generated UI.

Example:

```json
{
  "resourceAlias": "settlementCases",
  "statusMap": {
    "created": "opened",
    "requires_payment_method": "needsSource",
    "requires_confirmation": "approvalQueue",
    "processing": "routing",
    "authorized": "reserved",
    "captured": "collected",
    "settled": "cleared",
    "failed": "rejected",
    "canceled": "voided",
    "refunded": "returned"
  },
  "fieldMap": {
    "paymentId": "caseRef_a81d",
    "amount": "grossTotal_20c9",
    "currency": "moneyUnit_4ba2",
    "status": "caseState_f19e"
  }
}
```

The AI-generated UI should receive this mapped contract and sample payloads, so
the generated code naturally integrates with the public facade instead of
learning the internal core.

## Data Flow

```text
Admin creates brand
  -> Brand Runtime creates ContractVersion
  -> AI Gateway generates UI artifact from public contract
  -> Artifact validator checks files, imports, API usage, and manifest
  -> Brand Runtime publishes artifact version
  -> Admin opens /b/:brandPublicId/:contractSlug/app
  -> Generated UI calls only brand facade endpoints
  -> Brand Runtime maps external payloads to canonical DTOs
  -> Payment Core executes state changes and stores history
  -> Brand Runtime maps canonical responses back to brand contract
```

- keep existing layout builder code as the migration base;
- replace `LayoutBuilderDashboardConfig` with payment history and action DTOs;
- move current schema generator into a generic contract generator;
- add `ContractVersion` persistence;

MVP progress:

- admin-facing AI brand creation is available through the builder frontend and
  `POST /brands/ai`;
- the local generator creates brand runtime metadata: resource alias, status
  map, action labels, visual direction, contract summary, admin prompt, and
  system prompt;
- existing deterministic dashboard preview now reads generated metadata when it
  exists.
- brand runtime facade endpoints are available under
  `/brands/:id/:slug/runtime/*` and integrate generated brands with
  `payment-core` for registration, login, payment creation, and history.
- `apps/brand-runtime` now hosts the user-facing React/Vite merchant
  application for generated brands. It provides merchant login/registration,
  overview, payments, customers, and balances routes and calls only the brand
  runtime facade.

  methods, balance transactions, payment intents, and existing payment rows;
- the React brand runtime sends structured customer and payment method payloads
  through the facade instead of packing those values into `destinationLabel`.
- first-class read endpoints are available in `payment-core` and the brand
  facade for customers, payment methods, payment intents, and balance
  transactions. Payment creation still owns customer/payment-method creation in
  this MVP slice.
- the admin contract inspector now loads a live resource snapshot for the
  selected brand and shows merchant/account/payment/customer/method/intent/
  balance counts plus recent payments.
- local admin links now open the React brand runtime directly on
  `http://localhost:3006` instead of the builder proxy path.
- the admin console can seed a selected brand with demo merchant data covering
  settled card payment, bank review, declined card, authorization reserve, and
  refunded wallet scenarios.
- seeded demo data can be reset from the admin console, and the selected brand
  can be opened directly as the seeded demo merchant through a one-time runtime
  session token.

Immediate next actions:

2. Split `PaymentUser` into clearer merchant-owner and future customer auth

## Provider Research Notes

- OpenAI has an official TypeScript/JavaScript SDK (`openai`) and supports
  structured outputs/function calling for schema-bound responses and tool/API
  integration.
- Google recommends the Google GenAI SDK for Gemini; the JavaScript package is
  `@google/genai`, and Gemini supports structured outputs and function calling.
- Anthropic provides an official TypeScript SDK and Claude tool use with strict
  tool schemas.
- Vercel AI SDK Core provides a unified TypeScript API across supported
  providers for text generation, structured objects, tool calls, and agents.

## Key Decisions

- Use the existing layout builder only as a starting point for brand contracts
  and visual identity; do not keep it as the payment owner.
- Use a real payment-core service before generated UIs become first-class.
- Generate UI against brand facade contracts, not against the internal payment
  core.
- Keep provider APIs server-side and optional; local fallback must still work.
- Treat contract variation as encapsulation and tenant customization, not as a
  security boundary.
